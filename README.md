# z-compliance-review-service

## Overview

z-compliance-review-service is a Spring Boot–based microservice that performs compliance review in a GenAI multi-agent system.

It is designed as **Agent C** in the architecture, responsible for:

- Making **deterministic compliance decisions** using rule-based logic
- Generating **LLM-assisted explanations** for better user experience
- Retrieving compliance context from **pgvector (PostgreSQL)**
- Processing requests asynchronously via **Kafka**

---

## Key Responsibilities

- Evaluate customer eligibility based on policy rules
- Enforce KYC, risk, and income constraints
- Ensure decisions are **auditable and reproducible**
- Generate human-readable explanations using LLM
- Maintain compliance history

---

## Architecture Role

```text
z-wealth-knowledge-rag (Agent A)
        |
        | Kafka (event)
        v
z-compliance-review-service (Agent C)
        |
        | REST
        v
z-customer-data-service (Agent B)
```

---

## Core Design Principle

- Rules decide, LLM explains.
- Decision is made by rule-based logic (deterministic)
- Explanation is generated by LLM (optional, non-critical)

## Rule Engine

Examples:

Reject if KYC is not VERIFIED
Reject if income below threshold
Reject if risk level not suitable
Approve otherwise

Example logic:

```java
if (!"VERIFIED".equals(customer.getKycStatus())) return REJECTED;
if ("HIGH".equals(customer.getRiskLevel())) return REJECTED;
if (customer.getAnnualIncome() < 30000) return REJECTED;
return APPROVED;
```

---

## LLM Integration

OpenAI → Ollama → Rule fallback

Uses LangChain4j
Calls OpenAI (or fallback to local Ollama)
Generates explanation only (not decision)

Fallback strategy:

1. Try OpenAI
2. Fallback to Ollama
3. If both fail → return rule-based explanation

---

## Vector Search

pgvector stores compliance documents and retrieves context for explanations,
improving grounding and reducing hallucinations.

---

## Data Storage

- PostgreSQL: compliance history
- pgvector: compliance knowledge
- Redis: short-term memory
- Kafka: async messaging

---

## Failure Handling

- Kafka retry / DLQ
- LLM fallback
- Graceful degradation if Redis unavailable
- Safe failure if customer data unavailable

---

## Security

- No sensitive data sent to LLM unnecessarily
- LLM cannot override decision
- Rule engine guarantees correctness
- Audit trail for all decisions

## Run

```bash
./mvnw spring-boot:run
```

The service starts at http://localhost:8083.

OpenAPI endpoints:

- Swagger UI: http://localhost:8083/swagger-ui.html
- OpenAPI JSON: http://localhost:8083/v3/api-docs

### Docker

Build the Java 25 image (the build runs the test suite):

```bash
docker build -t z-compliance-review-service:jdk25 .
```

Run it with host services available through `host.docker.internal`:

```bash
docker run --rm -p 8083:8083 \
  -e OPENAI_API_KEY="$OPENAI_API_KEY" \
  -e SPRING_DATASOURCE_URL=jdbc:postgresql://host.docker.internal:5432/appdb \
  -e SPRING_DATA_REDIS_HOST=host.docker.internal \
  -e SPRING_KAFKA_BOOTSTRAP_SERVERS=host.docker.internal:9092 \
  -e SERVICES_CUSTOMER_DATA_BASE_URL=http://host.docker.internal:8082 \
  z-compliance-review-service:jdk25
```
